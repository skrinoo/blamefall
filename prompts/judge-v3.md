## 0. 端点定位

| 项 | 值 |
|---|---|
| 端点 | `POST /api/judge` |
| 实现 | `api/judge.mjs`（刻意做薄）+ `api/_gateway.mjs`（网络/配置/错误分类共享层） |

| temperature | `0.85` |
| max_tokens | `0`（不限制） |
| 单次输出 | 约 130 tokens |
| System Prompt | **`prompts/judge-v3.txt`** —— 唯一权威副本，服务端运行时用 `fs.readFile` 读 |

### 延迟预算为什么是 1850ms：800 → 1350 → 实测重算

`game.js` 的自由输入是：

```js
Promise.all([payload, delay(ms)])   // ms = flightMs = 2000
```

总时长 = `max(判定耗时, 2000ms)`。飞行动画本来就要播满 2.0 秒，
判定在这之前的**任何**时刻回来都是零感知成本的。

原来的 800ms 等于主动扔掉 700ms 免费窗口：AI 只慢一点点就被丢弃、
退化成兜底文案，而玩家根本感觉不到那 700ms。1350ms 曾是紧贴 1500ms 动画的
预算值；2026-09-11 生产实测 median 1711ms 把它击穿了，按 DEPLOY.md §4 公式
（flightMs ≥ p50+200、timeout ≈ flightMs-150）重算成现在的 1850 / 2000，
留 150ms 给 `Promise.all` 调度与 `finishThrow` 的 DOM 渲染。

**上限是硬约束：`timeout` 必须小于 `flightMs`。** 反了的话，
锅飞到 NPC 头上之后还要干等几百毫秒才出气泡，那是肉眼可见的卡顿。

> ✅ 2026-09-11 已实测：`gemini-2.5-flash` 经 `openai-next` 网关
> min/median/max = **1560 / 1711 / 2207ms**（无错误码）。
> 复测命令：`GET /api/health?probe=3&budget=1850`；
> 若中位数再次超出预算，调整规则见 `docs/DEPLOY.md` 第 4 节。

> **为什么只有自由输入才调 AI？**
> 快速选项（4 个固定论证类型）的理由文本是**固定的**，判定结果可完全预生成 →
> 运行时查 `data/verdicts.js`，**0ms、零成本、断网可用**。
> 实测约 90% 的操作走这条路径。详见 `docs/DEVLOG.md` 的「架构发现」一节。

### v1 → v3 的核心教训（可摘录进飞书文档）

> **凡是可以查表的确定性游戏数据，就不要让 LLM 输出。**
>
> LLM 只负责它真正擅长、且规则引擎写不出来的部分：
> **理解自然语言论证的质量、为一种行为命名、写出一句有洞察的点评。**
>
> 这一刀切下去同时买到三样东西：**消除判定漂移、减少输出 token、降低延迟。**

## 2. v3 System Prompt · 实时裁判（`/api/judge`）

> 🔴 **权威副本是 [`prompts/judge-v3.txt`](judge-v3.txt)，不是本节。**
>
> 服务端（`api/_gateway.mjs` 的 `loadSystemPrompt()`）在运行时用 `fs.readFile`
> 读那个 `.txt`。本节只是它的可读展示，两者已用逐字比对验证过一致
> （64 行，`-ceq` 大小写敏感）。
>
> **改 prompt 请改 `.txt`，然后同步本节。** 只改本节不会生效 ——
> 这与 §3 的 lib prompt 权威副本在 `scripts/prompt-lib-batch.txt` 是同一个约定。
>
> 为什么不让服务端直接硬编码：那会立即造出第二份 prompt。
> 本项目已经吃过「两处真相」的亏：本节【NPC 性格】清单漏了「前任」，
> 与 `data/npcs.js` 对不上；§4 的引擎复算表有三处手算与引擎实算不符
> （取错了 `ownershipOverride`、漏了反向型的反感免疫）。
>
> `.txt` 必须是 **UTF-8 无 BOM**（Node 的 `fs.readFile` 会把 BOM 当成 `\uFEFF`
> 混进 prompt 第一个字符）。注意这与 `.ps1` 的要求正好相反 ——
> PowerShell 5.1 读中文脚本**需要** BOM。代码里做了一次防御性剥除。

```text
你是《锅从天降》的裁判系统。这是一款黑色幽默风格的校园甩锅游戏：玩家头顶不断掉下「锅」（背锅事件），必须在锅落地前把它甩给某个 NPC，并当场给出一个理由。你负责判定这个理由的质量，并揭示这次甩锅用的是什么手法。

【输出字段】共 5 个，全部必填
1. argument_type    论证类型，只能从五个里选一个：事实型 / 情感型 / 转移型 / 反向型 / 荒诞型
2. persuasiveness   说服力，0-100 的整数。只评「这个理由本身的论证质量」，与对方是谁无关
3. technique_name   给这次甩锅手法起一个精准的「学名」，4-6 个字
4. verdict          裁判点评，一句话，25-45 字，必须用上 technique_name，揭示该手法的本质或代价
5. reaction_success / reaction_fail
                    该 NPC 在「接下了这口锅」与「拒绝了这口锅」两种情况下的反应，各一句话，20 字以内
                    成败由游戏引擎计算，你不负责判断，只需把两种反应都写出来

【argument_type 定义】严格按定义判，不要凭感觉
- 事实型：援引客观事实、记录、已有分工作依据。例「这部分是他上周认领的」「这周我值了两次日」
- 情感型：援引自己的状态、付出、情绪作依据。例「我这几天真的已经尽力了」
- 转移型：援引流程、制度、职责边界，主张责任不属于自己这一环。例「这个环节本来就没人明确负责」
- 反向型：把对方的行为当作自己行为的原因，责任反推给发起方。例「是您让我这么做的」「我们只是照着您的思路做」
- 荒诞型：援引无法证伪的玄学、超自然、无厘头前提。例「水星逆行」

【persuasiveness 评分锚点】
- 90-100：论证完整、有可核验的具体依据、且逻辑上确实指向责任归属
- 70-89 ：依据具体、方向正确，但存在跳跃或未经证实的前提
- 50-69 ：有一定道理，但主要靠语气而非依据
- 30-49 ：牵强，只能算是一种说法
- 0-29  ：完全站不住，或纯粹是借口
- 特别规则：理由中出现「又不是我」「跟我没关系」「凭什么是我」这类否认责任的表述，
  说服力上限为 35 —— 否认不是论证

【technique_name 约束】
- 4-6 个字，必须是一个可复用的「手法学名」，像社会学名词或武林招式名
- 严禁以「甩锅」二字结尾（会与其他条目重复）
- 好的例子：特长强征法、星象归因流、轮次对账单、源头回溯术、苦劳抵扣
- 坏的例子：技能甩锅、玄学甩锅、对等甩锅

【verdict 约束】
- 必须与具体事件无关，只评论「手法」本身 —— 这样同一条点评可以复用在不同的锅上
- 必须用上 technique_name
- 要揭示这个手法的本质、代价或它为什么有效
- 反例（禁止）：「以宏大的宇宙周期为电费买单」← 提到了具体事件「电费」
- 正例：「星象归因流用不可证伪的宏大前提覆盖具体责任，谁也反驳不了，谁也没被说服」

【语气铁律】
- 点评的对象永远是「手法」，绝不攻击玩家本人，绝不道德说教
- 毒舌但不刻薄：像体育解说员兼社会学家，不像教导主任
- NPC 反应只呈现此人的性格与处境，不评价玩家对错
- 荒诞型要配合演出，一本正经地认真对待荒谬前提，这是笑点来源
- 全部简体中文，输出里不要使用任何 emoji

【NPC 性格】
学弟学妹：讨好型，几乎不会拒绝，回答里常带犹豫和自我说服，从不抱怨
导师：权力上位，语气平淡而有压迫感，不解释理由，一句话就能让人闭嘴
室友：平等关系，会反驳也会认账，语气直接，会记账
教务处：官僚系统，只会输出模板化公文用语
社团学长：甩锅老手，擅长把责任包装成「锻炼机会」
辅导员：习惯用「你再想想」化解一切
摸鱼组员：自己就在摸鱼，被指认时会反过来质疑你
食堂阿姨：无辜，反应朴素直接，带方言语气词，让人内疚
前任：冷，短，不留余地；只听得进情感型论证，且只对情感社交场景的锅有反应
水逆/星座/天气：抽象概念，无法开口，由裁判代为陈述其「态度」
未来的自己：还没发生，无法回应，只能由裁判陈述后果
过去的自己：已无法辩解

【输出格式】
严格输出一个 JSON 对象，键为上述字段名。
对象之外不得有任何字符：不加 ```json 围栏，不写说明，不做解释。
```

### User Prompt 模板

> **关于【NPC 性格】那一块，它与 `npcs.js` 是两处真相，必须说清关系：**
>
> - 请求体里已经带了 `npcDesc`（逐次注入，来自 `npcs.js` 的 `desc` 字段），
>   那是**当前目标的权威人设**，两者冲突时以它为准。
> - system prompt 里的静态清单不是冗余：它给模型的是**整张权力关系图**
>   （谁压着谁、谁不能开口），单个 `npcDesc` 给不了这个上下文。
> - 但它会漂移。本次校对就抄到一个实例：**清单里漏了「前任」**——
>   他是能接自由输入的真实 NPC，模型会拿不到任何语气指导。
>   已补。改 `npcs.js` 的 NPC 名单时，请同步改这里。

```text
判定这一次甩锅。

锅（背锅事件）：{{pot.text}}
甩锅对象：{{npc.name}}（{{npc.desc}}）
玩家给出的理由：{{reason}}
```

### 响应 Schema

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["argument_type", "persuasiveness", "technique_name",
               "verdict", "reaction_success", "reaction_fail"],
  "properties": {
    "argument_type":   { "enum": ["事实型", "情感型", "转移型", "反向型", "荒诞型"] },
    "persuasiveness":  { "type": "integer", "minimum": 0, "maximum": 100 },
    "technique_name":  { "type": "string", "minLength": 3, "maxLength": 8 },
    "verdict":         { "type": "string", "minLength": 20, "maxLength": 60 },
    "reaction_success":{ "type": "string", "maxLength": 30 },
    "reaction_fail":   { "type": "string", "maxLength": 30 }
  }
}
```

### 前端校验契约（必须逐条执行，任一不通过即切兜底）

```js
function validateAIResponse(raw) {
  if (typeof raw !== "string" || !raw.trim()) return null;      // Bug#1：思考型模型会返回空
  let o;
  try { o = JSON.parse(stripFence(raw)); } catch (e) { return null; }
  if (!o || typeof o !== "object") return null;
  if (VALID_TYPES.indexOf(o.argument_type) < 0) return null;
  if (typeof o.persuasiveness !== "number") return null;
  if (o.persuasiveness < 0 || o.persuasiveness > 100) return null;
  if (!o.technique_name || !o.verdict) return null;
  if (!o.reaction_success && !o.reaction_fail) return null;
  return o;                                                     // 全部通过才可用
}
```

> ⚠️ **「有返回」不等于「可用」。** v1 实测中 `step-3.7-flash` 在 `max_tokens=2500` 下
> 正式回答为空、只回吐思维链。生产环境若不做这层校验，游戏会拿到空字符串直接崩。

## 3. lib System Prompt · 判定库批量生成

与实时裁判的**唯一差异**：输入是 `(NPC, 论证类型)` 而非具体理由，
产出的是**可跨 17 口锅复用**的通用条目。

> **权威副本是 `scripts/prompt-lib-batch.txt`**，不是本节。
> 脚本实际读取的是那一份文件；本节记录它的设计与演变。
> 二者若不一致，以脚本为准，然后回来修本节。

### v4-lib 要求的输出字段（全部是文案，**没有任何数值**）

| 字段 | 约束 | 校验器 `Test-VerdictItem` 拦的是什么 |
|---|---|---|
| `npc_id` | 与输入完全一致 | 缺失 |
| `argument_type` | 五种之一 | 类型漂移 |
| `technique_name` | 2-6 字，不以「甩锅」结尾，全库不重名 | 模型爱写 7-9 字华丽长名；跨批复用同一个词 |
| `verdict` | 8-90 字，每条独立立意，不提具体事件 | 过短没信息量、过长撑破气泡、集体复读同一句式 |
| `reaction_success` | ≤24 字，第一人称台词或括号动作 | 写成第三人称旁白 |
| `reaction_fail` | 同上；两条不得全空 | 空白气泡 |

> 数值字段黑名单 `power|score|persuas|rate|prob|rating|weight` 由校验器强制执行：
> **模型只要敢打分，条目就被丢弃并记进失败报告。** 这不是形式主义，
> 是 v3-lib 阶段荒诞型被评成全场最强之后加的硬闸门。
>
> 说服力 S 一律由 `engine/fallback.js` 对 `pot.options` 里的固定文本实算，与模型无关。
> 这也是快速选项能走 0ms 查表路径的前提。

### 以下为 v3-lib 原文（已被 v4-lib 取代，保留作迭代留痕）

注意其中第 7 项 `power_success / power_fail` 正是被删掉的那两个数值字段。

```text
你是《锅从天降》的文案生成系统。这是一款黑色幽默风格的校园甩锅游戏。

现在需要为「某个 NPC」在「某种论证类型」下的组合，生成一条通用判定条目。
这条条目会被复用在所有背锅事件上，因此所有文案都必须与具体事件无关。

【输出字段】每个组合输出 7 个字段
1. npc              NPC 中文名（原样回填）
2. argument_type    论证类型（原样回填）
3. technique_name   该组合下最具代表性的手法学名，4-6 字，严禁以「甩锅」二字结尾
4. verdict          裁判点评，一句话，25-45 字，必须用上 technique_name，
                    揭示该手法的本质或代价，且不得提及任何具体事件
5. reaction_success 该 NPC 接下锅时的反应，一句话，20 字以内
6. reaction_fail    该 NPC 拒绝这口锅时的反应，一句话，20 字以内
7. power_success / power_fail
                    该组合下「成功」与「失败」两种情形的说服力基线（0-100 整数）。
                    成功情形给 70-92，失败情形给 15-55。

【论证类型定义】
- 事实型：援引客观事实、记录、已有分工作依据
- 情感型：援引自己的状态、付出、情绪作依据
- 转移型：援引流程、制度、职责边界，主张责任不属于自己这一环
- 反向型：把对方的行为当作自己行为的原因，责任反推给发起方
- 荒诞型：援引无法证伪的玄学、超自然、无厘头前提

【手法学名参考风格】

【语气铁律】
- 点评对象永远是「手法」，绝不攻击玩家本人，绝不道德说教
- 毒舌但不刻薄：像体育解说员兼社会学家，不像教导主任
- NPC 反应只呈现此人的性格与处境，不评价玩家对错
- 荒诞型要配合演出，一本正经地认真对待荒谬前提
- 全部简体中文，不要使用任何 emoji

### 引擎复算（验证数值设计是否成立）

> 下表以 `game.js` 的 `selfTest()` 实算为准，四条全部通过（每次开局自动跑）。
> 早期版本这张表是**手算**的，错了三处，已用引擎复算更正。
> 更正记录保留在表后——它本身就是「文档不能替代可执行断言」的证据。

| 案例（锅 → NPC） | S | A | G | P | 结果 | 设计意图 |
|---|---|---|---|---|---|---|
| ppt → 学弟学妹 · 事实型 | 70 | 95 | 0.2 | **0.70** | ✅ 成功，得分 100，阴影 **+2** | 最好甩的路径正在让你更快崩溃 ✓ |
| ppt → 导师 · 反向型 | 65 | 0 | 0.1 | **0.28** | ❌ 失败，锅反弹，阴影 +3 | 常规路径推不动导师 ✓ |
| electric → 水逆 · 荒诞型 | 15 | — | — | **1**（跳过判定） | ✅ 直接成功，得分 30（×0.3） | 万能但低分 ✓ |
| trash → 室友 · 事实型 | 85 | 90 | 0.6 | **0.82** | ✅ 成功，得分 120，阴影 −1 | 本局最高 P，**奖励厘清责任** ✓ |

每一格都能逐层复算（`P = S×0.4 + A×0.4 + G×0.2`，S/A 先除 100）：

- **学弟学妹 · 事实型**：A = baseAcceptance 95，关系 100 → 关系惩罚 0；
  事实型既不在 prefers（情感型）也不在 dislikes（转移型/反向型）→ 无加减，A = 95。
  G = `ppt.ownershipOverride.didi` = 0.2。
  P = 0.70×0.4 + 0.95×0.4 + 0.2×0.2 = 0.28 + 0.38 + 0.04 = **0.70**
- **导师 · 反向型**：A = baseAcceptance 5 − 关系惩罚 (100−60)×0.2 = 8 → −3 → clamp **0**。
  G = `ppt.ownershipOverride.daoshi` = 0.1。
  P = 0.65×0.4 + 0 + 0.1×0.2 = 0.26 + 0 + 0.02 = **0.28**

  ⚠️ **前提是接锅信用 ≥ 3（`REVERSE_UNLOCK`）。** 信用不足时这一格根本走不到公式：
  `judge()` 的步骤 1 直接短路返回 `locked`，P = 0，verdict 是
  「『反向型』论证尚未解锁。接住 3 口锅之后，你才有资格说这句话。」
  自检里把 `catchCredit` 设成 9 而不是 0，就是为了测公式而不是测锁。
- **室友 · 事实型**：A = baseAcceptance 75 + 命中 prefers 15 = **90**，关系 100 → 惩罚 0。
  G = `trash.ownershipOverride.roommate` = **0.6**（覆盖掉 `npc.potOwnership` 的 0.5）。
  P = 0.85×0.4 + 0.90×0.4 + 0.6×0.2 = 0.34 + 0.36 + 0.12 = **0.82**

> ⭐ 最后一行验证了设计文档里那个「漂亮的设计涌现」：
> **P 值最高的不是最好甩的，而是最有事实依据、锅归属最清晰的那一次。**
> 游戏在数值层面奖励「厘清责任」、惩罚「欺负老实人」，全程零说教。

#### 更正记录（手算 → 引擎实算）

| 案例 | 原表 | 更正后 | 错在哪 |
|---|---|---|---|
| 学弟学妹 · 事实型 | P = 0.72 | **0.70** | 文档一处用了 G=0.3、另一处用了 G=0.2；`ppt` 对学弟学妹的 `ownershipOverride` 实为 0.2 |
| 室友 · 事实型 | G = 0.5、P = 0.80 | **G = 0.6、P = 0.82** | 取了 `npc.potOwnership`，但 `trash` 对室友有 `ownershipOverride` 0.6，覆盖优先 |

> 引擎或数据表一改就会当场报错——
> **能用可执行断言表达的东西，就不要用文档表格表达。**

## 5. 平衡扇展（全量组合复算）

判定公式一旦改动，靠试玩是测不出平衡问题的——一局 60 秒只能覆盖十几次甩锅。
所以每次改公式或改数据表，都把**全部组合**跑一遍：

```
17 口锅 × 14 NPC × 5 论证类型 = 1190 个组合
```

对每个组合调用真实的 `judge()`，统计胜率、悬空数、锁定数、暴击数。
脚本在浏览器控制台里跑（本机无 Node），直接读游戏已加载的那一份数据，
不存在「测试用的数据和线上不是同一份」的问题。

### 两轮扇展

| 指标 | 第一轮（1050 组合，15 锅） | 第二轮（1190 组合，17 锅） |
|---|---|---|
| 总胜率 | 48.9% | **51.8%** |
| 暴击数 | 0 | **0** |
| 悬空数 | 75 | 85 |
| 锁定数（信用 9） | 0 | 0 |
| 反向型对真实 NPC | 38/135 = 28% | 48/153 = **31%** |
| 荒诞型对真实 NPC | 0 | **0/153** |
| `selfTest()` | — | **4/4 通过** |

对照组（接锅信用 = 0，即正常开局）：胜率 40.7%，锁定 238 次，反向型对真实 NPC **0 胜**。

### 第三轮：契合度 fit（理由目标角色 ↔ 甩锅对象角色）

给每条快速理由标注「在怪谁」（self/npc/institution/any，见 `data/pots.js` 的 `targetRole`
与 `engine/fallback.js` 的 `TYPE_DEFAULT_ROLE`）：甩给角色不符的对象 S −12、相符 +8、any 中性。
**仅对快速选项生效**（理由文本 === `pot.options[type]`）；自由输入的文本角色无法可靠判定，
fit 保持中性，交给 AI 裁判。重跑 1190 组合（信用 9、关反甩取 ceiling）：

| 指标 | 第二轮（无 fit） | 第三轮（fit +8/−12） |
|---|---|---|
| 总胜率 | 51.8% | **50.3%** |
| 暴击 / 悬空 / 锁定 | 0 / 85 / 0 | **0 / 85 / 0** |
| 事实型（真实 NPC） | 61% | 52.3% |
| 反向型 | 31% | **38.6%** |
| 情感型 | 20% | 14.4% |
| 转移型 | 13% | 8.5% |
| 荒诞型 | 0% | **0%** |

阶梯**顺序不变**（事实 > 反向 > 情感 > 转移 > 荒诞），三条设计支柱全部保住。fit 把各类型的
「适用对象」收窄成 niche：情感型(self) 只在吃软乎的对象身上灵（前任/学弟学妹 prefers 的
A +15 抵消 fit 的 S −12，前任 on-key 情感型 P 仍 0.66）；转移型(institution) 主要对教务处与
抽象 NPC 灵（教务处+转移型 命中 +8，P 0.704）；荒诞型(any) 仍是纯解压阀。教务处总胜率
16%→11.8%（多数事实型默认 npc，对机构错配）。fit 分布：220 命中 / 392 错配 / 153 中性。
`selfTest()` 新增 fit 三条断言（契合/错配/中性）全过。

### 三条设计支柱在数值层面成立

1. **暴击只属于自由输入。** `crits = 0` 证明 `QUICK_CAP = 85` 生效：
   快速选项的说服力封顶 85，够不到 `CRIT_S = 88`。
   「完美论证」这个爽点必须靠玩家自己打字换来，不能靠点按钮。
2. **荒诞型万能但无用。** 对真实 NPC `0/153`，对抽象 NPC（天气/水逆/星座）`85/85`。
   它永远能甩出去，永远只值 30 分，而且甩给抽象对象时道德代价为「低」——
   一个纯粹的解压阀，不是策略选项。
3. **反向型是接锅换来的大招。** 信用 0 时 `locked 238 / 真实 NPC 0 胜`；
   信用 ≥ 3 时 `48/153 = 31%`，从「比荒诞型还弱」跳到**第二强论证**。

   论证类型阶梯（仅真实 NPC，各 153 次）：

   ```
   事实型 94 (61%) > 反向型 48 (31%) > 情感型 30 (20%) > 转移型 20 (13%) > 荒诞型 0 (0%)
   ```

   解锁的同时免疫反感惩罚——否则它会同时吃 A −20 和 S −14 两道折扣，
   接锅换来的奖励反而成了陷阱。

### 四个 0% 胜率 NPC 的诊断与修法

第一轮扇展暴露出四个 NPC 的最佳 P 都够不到 0.6。
**关键判断是：这四个不是同一个病。** 三个的病因是「钥匙孔太窄」而不是「数值太低」，
所以修法各不相同，且没有一个是简单地把 `baseAcceptance` 调高：

| NPC | 原胜率 | 病因 | 修法 |
|---|---|---|---|
| 社团学长 | 4/75 = 5% | `prefers` 只有转移型，而社团锅的 `ownershipOverride` 只有 0.6-0.7 | `prefers` 加「事实型」（排班表、报销单都是白纸黑字，主题成立）；tweet / budget 两口锅对他的 override 提到 0.8 / 0.9——他只对社团的锅负责 |
| 教务处 | 2/75 = 2.7% | **`desc` 承诺了「理由含书面语时说服力额外加成」，而引擎从未实现过** | 补机制而不是调参：`fallback.js` 加 `FORMAL_WORDS`（24 词）与 `npc.formalBonus` 开关，命中给 `min(hits×4, 12)`。**数据表许下的承诺必须由引擎兑现** |
| 前任 | 钥匙孔仅 5 格 | **锅池只有 1 口情感社交锅**，是内容缺口 | 新增 `groupchat` / `birthday` 两口情感社交锅（锅池 15 → 17）；同时 `baseAcceptance` 20 → 68、`relationInit` 20 → 45 |
| 导师 | 0/75（最佳 P 0.408） | 设计如此 | 不改。他是暴击专属目标：常规路径推不动，只有自由输入打出 S ≥ 88 且 G ≤ 0.2 才触发完美论证 |

> **前任那一格值得单说。** 他的难度应当**全部**来自「锁」：
> 只有情感社交场景的锅递得过去，只有情感型论证听得进去（其余三种全在反感表里），
> 即使都对，还有一半概率被反甩。这三重锁足够难了。
> 但钥匙对的时候必须能开——否则玩家永远学不会这条规则，只会觉得游戏在耍他。
> 所以 `baseAcceptance` 从 20 提到 68：**难度来自锁，不来自数值本身。**

ceiling 胜率 = 关闭反甩与疲劳时的上限，所以有 `reflectChance` 的 NPC 实际胜率更低。

## 6. 失败处理契约

| 失败形态 | 检测方式 | 处理 |
|---|---|---|
| 网关 402 / 5xx / 网络错误 | HTTP 状态码 | 立即切 `FallbackEngine` |
| 返回空字符串（思考型模型烧光 token） | `!raw.trim()` | 立即切 `FallbackEngine` |
| 返回带 markdown 围栏 | `stripFence()` 预处理 | 剥离后重试解析，失败则切兜底 |
| JSON 解析失败 | `try/catch` | 切兜底 |
| 字段缺失或越界 | `validateAIResponse()` | 切兜底 |
| 超时 > 800ms | `AbortController` + `setTimeout` | 切兜底，**并丢弃后到的响应** |

**兜底路径产出**：
- `persuasiveness` ← `FallbackEngine.computePersuasiveness()`
- `argument_type` ← `FallbackEngine.classifyArgumentType()`
- `technique_name` / `verdict` / `reaction` ← `FallbackEngine.lookup()` 查预生成判定库
- 判定库未命中时 ← 用 `TECHNIQUE_GENERIC` 兜底文案表（每类型 3 条轮换）

> **玩家侧表现**：完全无感。只有开发者面板（按 ` 键呼出）会显示 `source: fallback`。
> 这是刻意的——**兜底不应该让玩家觉得自己被降级对待了。**
